Hardware Identification and Functional Mapping

Objective: Study CPU, GPU, memory, buses, and interconnects; correlate with architecture diagrams.
lscpulspcidmidecode WSL2CPU-ZGPU-Z
📖Theory

A computer system is a collection of hardware components that communicate through well-defined interfaces. Understanding the physical layout and functional roles of these components is the foundation of computer architecture.

CPU (Central Processing Unit)

  • Cores & Threads: Physical execution units; SMT/Hyper-Threading doubles logical threads per core.
  • Clock Speed: Base & Boost frequencies in GHz; governed by thermal & power headroom.
  • IPC: Instructions Per Cycle – architectural efficiency metric independent of frequency.
  • Cache Hierarchy: L1 (≈32–64 KB, ~4 cycles), L2 (≈256 KB–1 MB, ~12 cycles), L3 (≈8–64 MB, ~40 cycles).
  • TDP: Thermal Design Power – sustained power envelope the cooler must handle.

Memory Subsystem

  • DRAM Types: DDR4 / DDR5 – double data rate; transfers on both clock edges.
  • Channels: Dual/Quad channel doubles memory bandwidth.
  • Ranks & Banks: Physical organization within a DIMM; affects timing & interleaving.
  • Latency (CL): CAS Latency – cycles between column address strobe and data output.
  • ECC: Error-Correcting Code – detects and corrects single-bit flips (server/workstation).

Buses & Interconnects

  • PCIe: Peripheral Component Interconnect Express – point-to-point serial link. Gen 4 x16 = 64 GB/s.
  • DMI/UPI: Intel's CPU-chipset (DMI) and CPU-CPU (UPI) links on multi-socket systems.
  • NVLink: NVIDIA's GPU-GPU interconnect – up to 900 GB/s (H100 NVLink 4.0).
  • USB / SATA / M.2: Peripheral and storage buses with varying bandwidth.
  • NUMA: Non-Uniform Memory Access topology on multi-socket systems.

GPU Architecture Overview

  • SM (Streaming Multiprocessor): GPU's core compute unit; contains CUDA cores, tensor cores, warp schedulers.
  • VRAM: Video RAM – GDDR6/HBM2e; separate from system RAM with dedicated bandwidth.
  • PCIe Lane: GPU connects to CPU via PCIe slot; bandwidth-limited vs CPU compute.
  • Driver Stack: Hardware → Kernel Mode Driver → CUDA Driver → CUDA Runtime → Application.

Functional Mapping: Von Neumann vs Harvard Architecture

Modern CPUs are fundamentally Von Neumann machines (shared instruction/data memory) but use Harvard-style L1 caches (split I-cache and D-cache) internally. The memory hierarchy exists because DRAM latency (~100 ns) is orders of magnitude higher than CPU cycle time (~0.3 ns at 3 GHz). Caches bridge this gap using locality of reference: spatial locality (nearby data accessed soon) and temporal locality (recently accessed data accessed again).

System Disassembly and Assembly

Objective: Identify and reassemble system components emphasizing bus/pipeline data paths.
ESD SafetyPCIeDDRSATAM.2 NVMe
📖Theory

Physical disassembly reinforces the abstract bus-and-pipeline model. Each component slot corresponds to a specific interconnect: DIMM slots ↔ memory bus, PCIe slots ↔ serial point-to-point lanes, M.2 slots ↔ PCIe or SATA lanes routed through the platform controller.

Bus Types by Physical Connector

  • DIMM (Long slot): 288-pin DDR4 or 288-pin DDR5; keyed differently. 240-pin DDR3 is shorter.
  • PCIe x16: GPU slot; 164 pins; runs x16 or x8 electrically despite physical x16.
  • PCIe x1/x4: Shorter slots; NICs, capture cards, NVMe adapters.
  • M.2 2280: 80mm card; supports NVMe (PCIe) or SATA depending on key (M-key = NVMe/SATA, B-key = SATA/USB).
  • U.2: Enterprise NVMe in 2.5" form factor; same signal as M.2 NVMe.

Data Path Pipeline

  • CPU ↔ DRAM: Via integrated Memory Controller (IMC) on modern CPUs; eliminated FSB bottleneck.
  • CPU ↔ GPU: PCIe root complex → PCIe slot; DMA for large transfers.
  • CPU ↔ SSD (M.2 NVMe): PCIe lanes from CPU or chipset → NVMe controller → NAND flash.
  • CPU ↔ Chipset: DMI (Intel) or Fusion Controller Hub link; all USB/SATA/slower PCIe flows through here.
  • Chipset ↔ USB/SATA: Legacy peripherals; max 600 MB/s (SATA III), 10 Gbps (USB 3.2 Gen 2).

1

Document before opening

Photograph the system from multiple angles, note all cable connections, and record the component layout. This is your reference for reassembly.

2

Shut down OS → power off PSU switch → unplug cable → press power button for 3 seconds → clip ESD strap to chassis metal.

3

Remove side panel and photograph interior

Note: front panel headers (power, reset, HDD LED), fan headers, PCIe power cables to GPU, SATA cables, and 24-pin ATX + 8-pin CPU connectors.

4

Remove GPU

Disconnect PCIe power connector(s). Release the PCIe slot retention clip (on motherboard). Unscrew bracket from case. Lift GPU straight up. Note which PCIe slot it occupied (primary x16 slot closest to CPU).

5

Remove RAM DIMMs

Press both retention clips simultaneously until DIMM pops up. Note slot population: for dual channel, DIMMs go in matched slots (e.g., A2+B2 per Intel, not A1+A2). Record which slots were populated.

6

Remove storage (M.2 and SATA)

M.2: Remove the single screw at the far end, lift at 30° angle, slide out. Note key type (M-key, B+M-key) and length (2242/2260/2280). SATA: unclip data cable, unplug power connector from drive.

7

Remove CPU cooler and CPU (optional)

Cooler: loosen screws/push-pins in an X pattern. CPU: lift ZIF socket lever (Intel LGA) or rotate lever (AMD AM4/AM5). Handle CPU by edges – never touch the pins on LGA sockets or pads on CPUs.

Instruction Pipelining Simulation (gem5 / Multi2Sim)

Objective: Model and visualize instruction-level parallelism (ILP), branch prediction, and hazards.
gem5Multi2SimILPBranch PredictionHazards
📖Theory

Pipelining overlaps the execution of multiple instructions by dividing the execution process into discrete stages. A classic 5-stage RISC pipeline (IF → ID → EX → MEM → WB) achieves CPI ≈ 1 in the ideal case, compared to CPI = 5 for sequential execution.

Pipeline Stages (Classic 5-Stage)

  • IF – Instruction Fetch: Read instruction from I-cache using PC; increment PC.
  • ID – Instruction Decode: Decode opcode; read registers from register file; detect hazards.
  • EX – Execute: ALU operation; address calculation for load/store; branch condition evaluation.
  • MEM – Memory Access: Read/write data cache for loads/stores. No-op for arithmetic.
  • WB – Write Back: Write result to destination register.

Pipeline Hazards

  • Structural Hazard: Two instructions need same hardware resource simultaneously. Solution: duplicate resources or stall.
  • Data Hazard (RAW): Read-After-Write: instruction needs result not yet written. Solution: forwarding/bypassing or stall (bubble insertion).
  • Data Hazard (WAR/WAW): Write-After-Read and Write-After-Write; less common in in-order pipelines.
  • Control Hazard: Branch outcome unknown until EX stage; pipeline fetched wrong instructions. Solution: branch prediction, delayed branching, or flush+stall.

Branch Prediction Schemes

Static Prediction

  • Always-taken or always-not-taken. Backward branches (loops) always taken = ~80% accurate for loops.
  • BTFNT: Backward-Taken Forward-Not-Taken heuristic.

Dynamic – 2-bit Saturating Counter

  • States: Strongly Not Taken → Weakly Not Taken → Weakly Taken → Strongly Taken.
  • Tolerates one misprediction without switching. ~90–95% accuracy typical.

Tournament Predictors

  • Combine local history (per-branch) and global history (gshare/gselect) predictors.
  • Meta-predictor chooses winner. Used in modern CPUs. ~97–99% accuracy.

ILP – Instruction-Level Parallelism

ILP is the potential for concurrent execution of instructions from a sequential program. It is bounded by data dependencies (RAW chains), control flow (branches), and memory ordering. Out-of-order (OoO) execution with register renaming (Tomasulo's algorithm) extracts ILP dynamically by executing independent instructions early and using a Reorder Buffer (ROB) to maintain the appearance of sequential execution.

/* hazard_test.c */
#include <stdio.h>
#include <stdlib.h>

/* RAW Hazard: each add depends on previous result */
long raw_chain(long n) {
    long a = 1;
    for (long i = 0; i < n; i++)
        a = a + a;  /* each iteration depends on previous */
    return a;
}

/* Branch-heavy: causes many branch predictions */
long branch_intensive(long n) {
    long sum = 0;
    for (long i = 0; i < n; i++)
        if (i % 3 == 0) sum += i;  /* unpredictable pattern */
    return sum;
}

int main() {
    printf("RAW result: %ld\n", raw_chain(1000000));
    printf("Branch result: %ld\n", branch_intensive(1000000));
    return 0;
}

Exp.04

Cache and Memory Hierarchy Analysis (gem5 / SimpleScalar)

Objective: Configure cache size, associativity, and replacement policy using simulators.
gem5AMATLRUFIFOValgrind
📖Theory

The memory hierarchy exploits locality of reference to bridge the gap between fast CPU registers and slow DRAM. Cache design involves three primary decisions: size, associativity, and replacement policy — each with distinct performance trade-offs.

Key Cache Parameters

Cache Size

  • Larger cache = higher hit rate but larger access latency and area cost.
  • Diminishing returns: doubling cache size rarely halves miss rate.
  • Working set size determines optimal cache size per application.

Associativity

  • Direct-mapped (1-way): One possible location per address. Fast but high conflict misses.
  • 2/4/8-way set-associative: Multiple ways per set. Reduces conflict misses at cost of comparator hardware.
  • Fully associative: Any line in any location. Eliminates conflict misses; hardware-intensive (CAM required).

Replacement Policies

  • LRU (Least Recently Used): Evict least recently accessed. Best average performance; expensive to track in high-associativity caches.
  • FIFO: Evict oldest line. Simpler hardware; Bélády's anomaly possible.
  • Random: Evict random line. Surprisingly competitive; no anomalies; simple.
  • PLRU (Pseudo-LRU): Binary tree approximation of LRU; used in real CPUs.

AMAT – Average Memory Access Time

textAMAT formula and example
AMAT = Hit Time + Miss Rate × Miss Penalty

Example (3-level hierarchy):
  L1: Hit Time = 4 cycles,  Miss Rate = 5%
  L2: Hit Time = 12 cycles, Miss Rate = 2% (of L1 misses)
  L3: Hit Time = 40 cycles, Miss Rate = 10% (of L2 misses)
  DRAM: 200 cycles

  AMAT = 4 + 0.05 × (12 + 0.02 × (40 + 0.10 × 200))
       = 4 + 0.05 × (12 + 0.02 × 60)
       = 4 + 0.05 × (12 + 1.2)
       = 4 + 0.05 × 13.2
       = 4 + 0.66
       = 4.66 cycles

Types of Cache Misses (3 C's)

Compulsory (Cold) Misses

  • First access to any data. Unavoidable without prefetching. Reduced by larger cache lines (spatial prefetch).

Capacity Misses

  • Working set larger than cache. Only reduced by larger cache size. Fully associative still has these.

Conflict Misses

#include <time.h>
#define N 1024

double A[N][N];

void row_major() {   /* Cache-FRIENDLY: sequential access */
    for (int i=0;i<N;i++)
        for (int j=0;j<N;j++)
            A[i][j] = i*j;
}

void col_major() {   /* Cache-UNFRIENDLY: stride-N access */
    for (int j=0;j<N;j++)
        for (int i=0;i<N;i++)
            A[i][j] = i*j;
}

int main() {
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    row_major();
    clock_gettime(CLOCK_MONOTONIC, &t1);
    printf("Row-major: %.3f ms\n", (t1.tv_nsec-t0.tv_nsec)/1e6);
    clock_gettime(CLOCK_MONOTONIC, &t0);
    col_major();
    clock_gettime(CLOCK_MONOTONIC, &t1);
    printf("Col-major: %.3f ms\n", (t1.tv_nsec-t0.tv_nsec)/1e6);
    return 0;
}

Exploration of GPU Architecture

Objective: Study CUDA cores, memory hierarchy, and parallelism using NVIDIA Nsight / Jetson developer tools.
CUDANsightnvidia-smiSMSIMT
📖Theory

GPU Execution Model

  • SIMT (Single Instruction Multiple Thread): All threads in a warp (32 threads) execute the same instruction simultaneously on different data. Analogous to CPU SIMD but with independent thread state.
  • Warp: The GPU's basic scheduling unit; 32 threads. A warp scheduler selects a ready warp each cycle.
  • Thread Block (CTA): Group of up to 1024 threads sharing fast shared memory (SRAM) and synchronization barriers.
  • Grid: Collection of thread blocks launched for a kernel; maps to all SMs on the GPU.

GPU Memory Hierarchy

  • Register File: Fastest; per-thread; 32-bit registers (~256 KB per SM). Register spilling to local memory is very slow.
  • Shared Memory (SRAM): L1-speed; shared within a thread block; configurable (16–100 KB per SM).
  • L1 Cache: Automatic; unified with shared memory on Ampere+.
  • L2 Cache: Shared across all SMs; ~40 MB on H100.
  • Global Memory (VRAM): GDDR6/HBM2e; 16–80 GB; ~1–3 TB/s bandwidth (HBM). High latency (~700 cycles).
  • Constant / Texture Memory: Read-only cached memory for broadcast patterns.

Streaming Multiprocessor (SM) Architecture

Each SM contains: CUDA cores (INT32, FP32, FP64), Tensor Cores (matrix multiply accelerators), warp schedulers, instruction dispatch units, the register file, shared memory, and L1 cache. An NVIDIA H100 has 132 SMs, each with 128 FP32 CUDA cores = 16,896 total CUDA cores. Occupancy is the ratio of active warps to maximum possible warps per SM – higher occupancy hides memory latency better.

Memory Coalescing

When 32 threads in a warp access global memory, the GPU combines (coalesces) these into a minimum number of 128-byte memory transactions. If threads access contiguous, aligned addresses: 1 transaction for all 32 threads. If threads access random addresses: up to 32 separate transactions, 32× slower. Always design kernels for coalesced access.

cudavector_add.cu – baseline CUDA kernel
#include <stdio.h>
#include <cuda_runtime.h>

// CUDA error checking macro
#define CUDA_CHECK(err) { \
  if (err != cudaSuccess) { \
    fprintf(stderr, "CUDA error at %s:%d: %s\n", \
      __FILE__, __LINE__, cudaGetErrorString(err)); \
    exit(1); } }

__global__ void vectorAdd(float* A, float* B, float* C, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N)
        C[i] = A[i] + B[i];  // Coalesced access – all good
}

int main() {
    int N = 1 << 20;  // 1M elements
    size_t bytes = N * sizeof(float);
    
    float *h_A = (float*)malloc(bytes);
    float *h_B = (float*)malloc(bytes);
    float *h_C = (float*)malloc(bytes);
    for (int i=0; i<N; i++) { h_A[i]=1.0f; h_B[i]=2.0f; }
    
    float *d_A, *d_B, *d_C;
    CUDA_CHECK(cudaMalloc(&d_A, bytes));
    CUDA_CHECK(cudaMalloc(&d_B, bytes));
    CUDA_CHECK(cudaMalloc(&d_C, bytes));
    
    CUDA_CHECK(cudaMemcpy(d_A, h_A, bytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(d_B, h_B, bytes, cudaMemcpyHostToDevice));
    
    // Launch: 256 threads/block, ceil(N/256) blocks
    int blockSize = 256;
    int gridSize = (N + blockSize - 1) / blockSize;
    vectorAdd<<<gridSize, blockSize>>>(d_A, d_B, d_C, N);
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaDeviceSynchronize());
    
    CUDA_CHECK(cudaMemcpy(h_C, d_C, bytes, cudaMemcpyDeviceToHost));
    printf("C[0]=%.1f (expected 3.0)\n", h_C[0]);
    
    cudaFree(d_A); cudaFree(d_B); cudaFree(d_C);
    free(h_A); free(h_B); free(h_C);
    return 0;
}

GPU Virtualization with Docker / NVIDIA Container Toolkit

Objective: Deploy and monitor GPU-enabled containers for workload isolation and sharing.
DockerNVIDIA Container ToolkitIsolationGPU Sharing
📖Theory

GPU virtualization enables multiple workloads or users to share a single physical GPU. Unlike CPU virtualization, GPU VMs historically required full hardware passthrough (vGPU/VFIO). The NVIDIA Container Toolkit (formerly nvidia-docker) provides a lightweight alternative: it mounts GPU drivers and devices into Docker containers, giving each container direct GPU access with namespace isolation.

Container vs VM GPU Isolation

  • Docker + Container Toolkit: Namespace isolation; shared GPU memory; near-zero overhead; no VM hypervisor. CUDA Context per container.
  • NVIDIA vGPU: Hardware-mediated partitioning; strict memory isolation; requires licensed vGPU driver (datacenter use); low overhead via SR-IOV on Ampere.
  • MIG (Multi-Instance GPU): Ampere+ hardware partitioning; divides SM and memory into independent instances; true isolation; no driver license needed.
  • CUDA MPS: Multi-Process Service; shares GPU between processes efficiently; reduces context switching overhead; no memory isolation.

Container Toolkit Architecture

  • Docker daemon → nvidia-container-runtime hook → mounts /dev/nvidia* devices and driver libraries into container.
  • Container sees GPU as if bare-metal; full CUDA support without installing GPU driver inside container.
  • Only CUDA toolkit (user-space libraries) needs to be in the container image.
  • Resource limiting: --gpus device=0 restricts to specific GPUs; CUDA_VISIBLE_DEVICES further limits visibility.

Amdahl's Law

textAmdahl's Law formula and implications
Speedup(n) = 1 / ( (1 - P) + P/n ) Where: P = fraction of program that can be parallelized (0 to 1) n = number of processors / parallel units (1-P) = serial fraction (bottleneck) Examples: P=0.90, n=4 → Speedup = 1/(0.10 + 0.225) = 3.08x P=0.90, n=∞ → Speedup = 1/0.10 = 10x (maximum possible) P=0.50, n=∞ → Speedup = 1/0.50 = 2x (severe serial bottleneck) Gustafson's Law (weak scaling): Speedup = n - (1-P)(n-1) Assumes problem size scales with processors. More optimistic for large-scale scientific computing.

CPU vs GPU Performance Characteristics

CPU Strengths

  • Low latency: ~ns for single instruction
  • Complex control flow; branch prediction
  • Large caches; random access patterns
  • Sequential code; OS/I/O; sparse computations
  • Typically 8-64 cores, 1-4 GHz

GPU Strengths

  • High throughput: thousands of cores in parallel
  • Dense, regular computation; no branch divergence
  • High memory bandwidth (1–3 TB/s vs CPU's ~100 GB/s)
  • Matrix multiply, convolutions, FFTs, Monte Carlo
  • FP32 peak: RTX 4090 = 82.6 TFLOPS vs i9-13900K = ~0.3 TFLOPS

#include <stdio.h> #include <omp.h> #include <time.h> #define N (1<<24) float A[N], B[N], C[N]; void serial() { for (int i=0;i<N;i++) C[i]=A[i]+B[i]; } void parallel() { #pragma omp parallel for simd schedule(static) for (int i=0;i<N;i++) C[i]=A[i]+B[i]; } double time_fn(void(*fn)()) { struct timespec t0,t1; clock_gettime(CLOCK_MONOTONIC,&t0); fn(); clock_gettime(CLOCK_MONOTONIC,&t1); return (t1.tv_sec-t0.tv_sec)+(t1.tv_nsec-t0.tv_nsec)/1e9; } int main() { for (int i=0;i<N;i++){A[i]=i;B[i]=N-i;} printf("Serial: %.3f s\n", time_fn(serial)); printf("Parallel: %.3f s\n", time_fn(parallel)); return 0; }

📖Theory

Power Dissipation in CMOS

Total CPU/GPU power is the sum of dynamic and static (leakage) power:

textPower consumption model
P_total = P_dynamic + P_static P_dynamic = α × C × V² × f where: α = activity factor (fraction of gates switching) C = switched capacitance V = supply voltage f = clock frequency P_static = I_leak × V (leakage current × voltage) Implications: • Reducing V by 10% reduces dynamic power by 19% (V²) • Reducing f by 10% reduces dynamic power by 10% but also allows lower V • Modern CPUs combine VFScaling: drop V AND f together for major power savings • At low utilization, static power dominates (justify sleep states)

TDP and Power States

  • TDP (Thermal Design Power): Sustained power the cooling solution must handle. NOT peak power (Turbo can exceed TDP briefly).
  • PL1 (Power Limit 1): Long-term (sustained) power limit ≈ TDP.
  • PL2 (Power Limit 2): Short-term boost limit; often 2-4× TDP for seconds.
  • C-states: CPU idle states (C0=active, C1=halt, C6=deep sleep). Each reduces power progressively.
  • P-states: Performance states; voltage/frequency operating points.
  • T-states: Thermal control; clock modulation (throttle) when thermal limit exceeded.

Performance Per Watt (PPW)

  • Primary metric in HPC, data centers, edge computing, and mobile.
  • PPW = Performance (FLOPS, IOPS, FPS) / Power (Watts)
  • GPU PPW often better than CPU for massively parallel tasks.
  • Apple M-series excels at PPW (ARM + process node + unified memory).
  • DVFS (Dynamic Voltage and Frequency Scaling) maximizes PPW by operating at the most efficient voltage-frequency knee.
  • Thermal throttling is the automatic PPW degradation when junction temperature (Tj) exceeds TjMax.

Thermal Throttling Mechanics

When junction temperature exceeds TjMax (typically 95–105°C for Intel/AMD, 85°C for GPUs), the hardware automatically reduces frequency via T-state clock gating. This creates a negative feedback loop: high load → high temp → throttle → lower perf → lower power → lower temp → unthrottle → repeat. Sustained throttling indicates inadequate cooling for the workload.
